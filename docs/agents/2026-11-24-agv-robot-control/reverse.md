# Управление ориентировкой, движением и вилами AGV

## 1. Вопрос
Как AGVControl задает позу рабочей точки и команду вил, и как симулятор интерпретирует эти значения, чтобы объяснить остановку робота под углом и неправильный выезд вил.

## 2. Точки входа
- Order path: `OrderService.MakeNodesAndEdgesForOrderAsync`, формирует Node/Edge DTO, actions и публикуемый order (`AGVControl/AGVControlApi/Data/OrderService.cs:1080`, `1176`, `1202`).
- Рабочий курс/позиция: `PositionBeforeWorkingNode` и `Node.AgvStopPositionXY` (`AGVControl/AGVControlApi/Data/OrderService.cs:1392`, `AGVControl/AGVModels/Def/Node.cs:182`).
- Order публикация через MQTT: `TuskSendOrderToAgvInternalAsync` (`AGVControl/AGVControlApi/Data/OrderService.cs:1455`, `1500`). Не проверено, что текущая конфигурация данного робота использует именно устаревший TUSK путь: метод помечен obsolete.
- Отдельный pick/drop instantAction: `ExecutePickDropAsync` (`AGVControl/AGVControlApi/Services/AgvInstantActionsService.cs:462`).
- Simulator: VDA движение/курс в `MotionController::integrate` и `VDARobotModel::doControl` (`sim/vdalogic/src/MotionController/MotionController.cpp:103`, `sim/robotssimulator/assets/VDARobots/VDAForkLiftPlugin/src/RobotsModel/VDARobotModel.cpp:100`).
- Вилы: `VDAForkLiftModel::integrate` (`sim/robotssimulator/assets/VDARobots/VDAForkLiftPlugin/src/RobotsModel/VDAForkLiftModel.cpp:538`).

## 3. Поток
1. Order выбирает рабочую точку и вычисляет входящий курс `theta` по входящему ребру или предыдущему узлу (`OrderService.cs:1145-1159`, `1392-1432`).
2. Для LOADING/UNLOADING action создается с `containerX/Y` равными координатам рабочей точки и `containerTheta=theta`; stop XY затем выбирается по близости к входной позиции (`OrderService.cs:1151-1159`, `1617-1673`; `Node.cs:182-201`).
3. Рабочая NodePosition получает рассчитанные XY и обычно рассчитанный theta, кроме WORKING, где theta явно сбрасывается в null (`OrderService.cs:1161-1162`, `1176-1191`).
4. Edge orientation первого ребра определяется `MoveDirection`; после первого существующего ребра локальная переменная сбрасывается в 0. Путь ссылается на сохраненную trajectory, при двустороннем ребре контрольные точки могут развернуться (`OrderService.cs:1200-1268`).
5. AGVControl публикует order в MQTT; отдельный instantAction pick/drop публикуется через `PublishInstantActionAsync`, без добавления в order node action (`OrderService.cs:1500-1502`; `AgvInstantActionsService.cs:497`). Ответ публикации подтверждает MQTT publish, а не завершение вилочной операции (`OrderService.cs:1505-1514`; `AgvInstantActionsService.cs:499-508`).
6. Симулятор при старте ребра берет node theta; если заданное отклонение превышает 10% `allowedDeviationTheta`, выставляет `needRotate`, и control loop поворачивает на required angle (`MotionController.cpp:128-149`; `VDARobotModel.cpp:130-139`). При торможении проверка повторяется (`MotionController.cpp:211-227`).
7. На node simulator ставит action breakpoint; после остановки ActionManager отдает node actions. Pick/drop проходит через simpleDrive, затем fork command и состояние RUNNING/FINISHED; autoReturnNode может вызвать отъезд назад (`MotionController.cpp:337-340`, `231`; `VDAForkLiftModel.cpp:538-614`, `119-137`).

## 4. Поля и значения
| Поле | Значение/происхождение | Где задано | Зачем |
|---|---|---|---|
| `nodePosition.theta` | На рабочем узле вычисленный `atan2(dy,dx)` от входа к паллете; `WORKING` превращает его в null. `WAYPOINT` тоже null, charging null (`OrderService.cs:1161-1173`). | `OrderService.cs:1149-1162`, `1176-1189` | Поза узла; simulator использует заданный theta для доворота (`MotionController.cpp:134-148`). |
| `orientation` | Первое ребро: `0` forward, `PI` backward из `order.MoveDirection`; последующие реальные рёбра принудительно `0`. | `OrderService.cs:1200`, `1258-1268` | С `TANGENTIAL` влияет на выбор driveBackward в simulator (`MotionController.cpp:172-178`). |
| `MoveDirection` | Сравнивает targetAngle с текущим `agvTheta`; forward если абсолютная разница < 100°, иначе backward. `startTheta` берет AGV theta, иначе theta стартового узла. | `OrderService.cs:1898-1917`, `1928-1957` | Начальная ориентация движения, не точный курс рабочей точки. |
| `PositionBeforeWorkingNode` | Единственный входящий node имеет приоритет над node из пути; theta = `Atan2(current-inNode)`. Иначе предыдущий узел; fallback из `CurrentNodeId` задает theta=0. | `OrderService.cs:1400-1442` | Определяет касательную ориентацию и точку, откуда выбирается рабочая сторона. |
| `AgvStopPositionXY` | Для forklift выбирает меньший квадрат расстояния между `Position +/- WrkLength*(cos(theta),sin(theta))`; tie выбирает Front. | `Node.cs:102-116`, `124-135`, `182-201` | Смещает позицию AGV вдоль курса к рабочей точке. Это не задает theta само по себе. |
| `containerTheta` узлового action | Равно рабочему `theta`, а X/Y равны исходным `positionX/Y` рабочего узла. | `OrderService.cs:1621-1651` | Поза контейнера для алгоритма вил/подъезда. |
| `containerTheta` instantAction | Расчетное значение из `adapter.MapPosition`; по замыслу текущий AGV theta. | `AgvInstantActionsService.cs:472-489` | Параметр отдельного action. Выражение `agv.PositionX ?? 0 + ...` из-за приоритета `??` выглядит как X=PositionX при ненулевом значении, без прибавки distance; аналогично Y. Это проверяемый дефект. |
| `allowedDeviationTheta` | Order задает max(значение узла, 0.1); для старта legacy order расширяет до 3.14. Симулятор подставляет 0.01, если входное значение нулевое. | `OrderService.cs:1188-1189`, `1471-1478`; `vdalogic/Structs.h:927-999` | Допуск ориентации; simulator для trigger использует `allowedTheta()*0.1` (`MotionController.cpp:141-148`). |
| `orientationType` | Order использует edge setting или `TANGENTIAL`; виртуальное ребро без orientation/type; `rotationAllowed` для реального ребра не копируется, виртуальному false. | `OrderService.cs:1221-1225`, `1258-1264` | Семантика edge orientation и право вращаться; simulator выбирает backward только для TANGENTIAL (`MotionController.cpp:172-178`). |
| `trajectory` | Десериализуется из `edge.Trajectory`; двусторонняя кривая разворачивается по dot product с направлением между узлами. | `OrderService.cs:1229-1246` | Геометрия движения по ребру. Simulator использует ее при >2 control points, иначе строит прямую по node positions (`MotionController.cpp:370-401`). |
| `onlyFork`, `autoReturnNode`, `noScan`, `adjustWithoutOA` | Узловой forklift action: true, true, false, true соответственно; ActionService default отдельно: true, false, true, true. | `OrderService.cs:1653-1669`; `ActionService.cs:703-752` | Режим вил/автовозврата/сканирования/корректировки. Настройки расходятся между генераторами. |
| `blockingType` | Для order pick/drop `SOFT`; instantAction publish вызывается отдельным механизмом. | `OrderService.cs:1629-1635`; `AgvInstantActionsService.cs:497` | Граница выполнения action в заказе. Параметр instantAction в этом месте явно не прочитан/не проверен. |

## 5. Отличия и дефекты
- Углы в AGVControl вычисляются стандартно в радианах `atan2(dy,dx)` относительно +X (`OrderService.cs:1369-1381`); 0 направлен +X, знак + идет к +Y по формуле. Node theta поэтому может быть 45° при диагональном входе, даже если рабочая цель визуально «смотрит» на стеллаж (`OrderService.cs:1412-1432`).
- `PositionBeforeWorkingNode` не читает `node.Theta` вообще для рабочих узлов. Единственный incoming graph node имеет приоритет над фактическим путем; у узла с одним, но неподходящим incoming направление получится неожиданным (`OrderService.cs:1407-1432`).
- В `MakeNodesAndEdgesForOrderAsync` начальное `theta = null` и комментарий с `node.Theta` закомментирован. Для `WORKING` рассчитанная theta затем очищается. Если рабочий тип приходит как WORKING, симулятор не получит требование смотреть на стеллаж (`OrderService.cs:1137-1139`, `1161-1162`).
- Текущий построитель пути выставляет `RotationAllowed` только для virtual edge false; для реального поля присваивание закомментировано. Реальный edge получает ориентацию 0 уже со второго ребра. Следует сверять фактически отправленный JSON, не только настройки ребра (`OrderService.cs:1221-1225`, `1258-1264`, `1267-1269`).
- Simulator преобразует курс `theta` напрямую в `dir=(cos(theta),sin(theta))`; визуальная модель отображает `theta*180/PI - 90` (`vdalogic/Structs.h:1581-1585`; `robotssimulator/src/Robots3D/customrobot.cpp:224`). В исследованных местах `inverseCoord` определен как swap x/y, но вызов не найден; направление этого преобразования не доказано (`MotionController.cpp:16-22`). Swap в конкретном импорт/рендер пути не проверен.
- Simulator выбирает backward для TANGENTIAL, если `orientation > PI/2`; решение не сравнивает угол с PI симметрично, поэтому отрицательные углы и диапазоны >2PI могут дать неверную классификацию (`MotionController.cpp:172-178`). В `VDARobotModel` при backward для контроля используется `mState.fi - PI` (`VDARobotModel.cpp:232-245`).
- В узловом order action симулятор исполняет simpleDrive до вил: при `noScan=false` вызывает `simpleDrive(0.3)`; при `noScan=true` переходит в ветку алгоритма подъезда. Затем `onlyFork` определяет обычная команда вил или InPlace (`VDAForkLiftModel.cpp:544-606`). Название `noScan` в коде фактически инвертировано относительно простого прочтения: true включает ветку скан/алгоритма.
- `autoReturnNode=true` симулятор после retract выполняет `simpleDrive(-0.3,true)`; false завершает action. У order default autoReturn=true, у `ActionService` default и instantAction false (`VDAForkLiftModel.cpp:119-137`; `OrderService.cs:1657-1660`; `ActionService.cs:741-747`; `AgvInstantActionsService.cs:480-488`).
- Возврат вилочного механизма не задает новый курс: использует простой задний отъезд; отдельная гарантия сохранения/восстановления theta после действия не найдена. В simulator после action конечный курс зависит от простого движения и контроллера, не от повторной команды node theta; не проверено на стенде.
- У `TuskAdapter` `effectiveContainerTheta` вычисляется, но в показанном order builder фактически не применяется к action: `actions` пусты. Поля `containerX/Y` тоже считаются, однако в nodes нет action, а результат не включает их отдельно (`TuskAdapter.cs:393-468`). Для этого конкретного builder проверить альтернативное использование API перед выводом о рабочем эффекте.
- TUSK `MapPosition` оставляет X/Y как есть и нормализует theta в [-PI,PI], без swap (`TuskAdapter.cs:91-104`). Для AGVControl иных адаптеров преобразования отличаются/не проверялись.
- Симулятор хранит `containerX/Y/Theta` напрямую из action; в просмотренном коде вилочная ветка читает `onlyFork`, `noScan`, `autoReturnNode`, но применение container pose в алгоритме не установлено (`vdalogic/Structs.h:1606-1619`; `VDAForkLiftModel.cpp:544-606`). Значит связь containerTheta с физическим доворотом симулятора не доказана.

## 6. Что повторить у нас
- Отделить целевую ориентацию машины от ориентации/координат груза: передавать node theta явно в рабочий узел и проверять, что не сбрасывается для типа WORKING.
- Не выводить курс только из единственного incoming edge без проверки выбранного ребра в заказе; выбирать фактический predecessor order.
- Перед отправкой логировать итоговые nodePosition(theta, x, y), edge(orientation, orientationType, rotationAllowed), trajectory и все параметры pick/drop после adapter mapping.
- Исправить/проверить выражение вычисления instantAction containerX/Y с явными скобками; сейчас при заданной PositionX/Y смещение вперед может не применяться.
- Унифицировать генераторы default actions и проверить противоречащие значения autoReturnNode/noScan; валидировать параметры на конкретном адаптере.
- Не рассчитывать, что `containerTheta` сам повернет кузов: подтвержденный механизм поворота симулятора берет `nodePosition.theta`; реальное поведение вил подтвердить измерением.

## 7. Что проверить на стенде
- До отправки/до выезда: снять из outgoing order и `visualization` поля `agvPosition.x/y/theta`, входной/предыдущий node XY, рабочий node XY/theta, `allowedDeviationTheta`, выбранный `moveDirection`, `edge.orientation`, `orientationType`, `rotationAllowed`, control points trajectory. Проверить единицы угла (радианы) и сравнить вычисленный `atan2` с theta стеллажа.
- До вил: из state снять `nodeStates[].nodePosition`, `edgeStates[].orientation/orientationType/trajectory`, `actionStates` и `driving`; из node action снять `actionType`, `blockingType`, параметры `containerX/Y/Theta`, `onlyFork`, `autoReturnNode`, `noScan`, `adjustWithoutOA`. Замерить фактическую позицию центра AGV и угол относительно нормали стеллажа.
- Во время выезда: снимать visualization `agvPosition.x/y/theta`, state `actionStates[].actionStatus`, fork `forkPos/liftPos`, action parameters; проверить, происходит ли движение корпуса до вил и направление (вперед/назад), сравнить с `noScan` и `onlyFork`.
- После действия: снять action status, `agvPosition.theta`, fork positions и текущий node/edge; измерить смещение корпуса при `autoReturnNode=true` и отдельно false. Проверить, вернулся ли курс к node theta или остался измененным.
- Сделать контрольный прогон с рабочим курсом 0°, затем 45° и 90° при одинаковом входе; отдельно изменить node.Theta, incoming-edge направление и containerTheta по одному. Если 45° совпадает с `atan2` входа, причина в выборе входного направления; если угол state верен, а модель повернута на 45° иначе, проверять визуальное преобразование осей/adapter.
- Конкретный стенд/робот и текущий сериализованный JSON не проверены; поля, доступные в реальном `visualization/state`, зависят от версии и adapter.
