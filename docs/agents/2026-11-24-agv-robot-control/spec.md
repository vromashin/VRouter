# Спека: привести VDA-заказ к эталону AGVControl (движение и вилы)

Дата: 2026-11-24. Ветка: `ai/stage2.5-vda-port-step3`, HEAD `84ef86c`.

## Цель

Заказ, который `VR.RoutePlanner` публикует роботу, должен совпадать по полям с заказом старого
AGVControl на том же маршруте. В первую очередь это касается действий вил и курса в узлах,
потому что именно они давали 45 градусов у стеллажа и неверную работу вил.

Ориентир, а не догма: A* может выбрать другой допустимый маршрут (например `wa63` вместо `wa177`),
это не расхождение. Сравниваются структура узлов, действия, курсы, допуски и поля ребер.

## Эталон

Снят с живого старого AGV на стенде 131 (симулятор), задача WMS `pick wo-2-7 -> drop wo-1-6`:

- `ref-pick-drop-wo-2-7-wo-1-6.json` - заказ старого AGV на маршруте `wo-2-7 -> wo-1-6`.
- `ref-rev-leg1-to-pick.json` - обратная задача, плечо подъезда к `wo-1-6`.
- `ref-rev-leg2-pick-drop.json` - обратная задача, плечо `pick wo-1-6 -> drop wo-2-7`.
- `our-same-route-order.json` - наш заказ на том же маршруте (`ORD_00184`).
- `evidence/same-route-diff.txt` - машинное сравнение эталона и нашего заказа.
- `evidence/analyze_shape.py`, `evidence/diff_same_route.py` - скрипты разбора.

Скрипты захвата: `evidence/capture_our.sh`, `evidence/capture_rev.sh`.

## Что должен делать эталон (проверено на 4 снимках)

1. Действие вил (`pick`/`drop`, `blockingType: SOFT`) стоит только в узле, где действие реально
   выполняется. В узлах, которые робот только проезжает или с которых уезжает, действия нет.
2. Курс рабочего узла с действием равен направлению от узла к контейнеру (`containerTheta`):
   `wo-2-7` (контейнер западнее) - `pi`, `wo-1-6` (контейнер восточнее) - `0`.
3. Первый узел сообщения - фактическая поза робота с допусками `0.3 / 3.14`; курс в нем есть,
   когда поза известна. У остальных узлов допуски `0.1 / 0.1`.
4. `containerX/containerY` - координаты паллеты, `containerTheta` - курс к ней.
5. На ребрах нет `maxSpeed` и `maxRotationSpeed`.
6. `orientation` первого ребра равен `pi`, когда робот начинает движение задним ходом
   (курс робота в стартовом узле противоположен направлению на следующий узел). У остальных
   ребер `0`. Наблюдения: `ref-pick-drop` ребро `801-wo-2-7-wa62` - `pi`;
   `ref-rev-leg2` ребро `801-wo-1-6-wa178` - `pi`; ребра к целевому рабочему узлу - `0`.

## Дефекты, которые надо устранить

### D1. Действие вил ставится на узел отправления (критично)

Файл: `src/VR.RoutePlanner.Infrastructure/Mqtt/VdaOrderBuilder.cs`, `BuildNode`, строки 259-308.

Сейчас действие добавляется на любой рабочий узел плана (`isWorking`). Заказ `ORD_00184`
(выгрузка в `wo-1-6`) начинается в `wo-2-7`, и в нем на `wo-2-7` стоит `drop`, хотя робот оттуда
только уезжает. В эталоне действие только у целевого узла.

Требуется: действие вил ставить только в узле, который является целью заказа, то есть в последнем
узле плана (`index == plan.Nodes.Count - 1`), либо в узле подхода при `isApproachFallback`.
Курс `theta` рабочего узла задавать по тому же признаку.

Ожидаемый результат для `ORD_00184`: узел `wo-2-7` без действия и без `theta`, узел `wo-1-6`
с `drop` и `theta = 0`.

### D2. Заказ с нулевым маршрутом теряет действие вил (критично)

Файл: `src/VR.RoutePlanner.Application/Robots/RobotOrderService.cs`, строки 237-264.

Сейчас при `from.Id == to.Id` создается заказ со статусом `Completed`, `PlanJson = "{}"`,
роботу ничего не публикуется. Заказ `ORD_00183` (`pick wo-2-7`, робот уже в `wo-2-7`) закрылся
мгновенно, `pick` не выполнялся, MQTT-заказа не было. В итоге робот делает `drop`, ничего не взяв.

Требуется: даже при совпадении стартового и целевого узла отправить заказ, в котором есть узел
с действием вил. Образец эталона - `ref-rev-leg2-pick-drop.json`, начало:
узел позы `wo-1-6` (`0.3 / 3.14`, без действия, без `theta`), затем второй узел `wo-1-6`
(`0.1 / 0.1`, `theta = 0`, действие `pick`), и виртуальное ребро `VIRTUAL_START_wo-1-6`
с `rotationAllowed: false`.

### D3. `orientation` первого ребра при выезде из рабочего узла

Файл: `VdaOrderBuilder.cs`, `BuildEdge`, строки 344-349.

Сейчас `orientation = first && link.Direction == RouteEdgeDirection.Backward ? pi : 0`.
Для `801-wo-2-7-wa62` (старт из `wo-2-7`, робот смотрит в стеллаж, едет назад) эталон дает `pi`,
у нас `0`. Это одно и то же ребро и то же направление, расхождение чистое.

Требуется: `orientation = pi`, если это первое ребро сообщения и направление от стартового узла
к следующему противоположно курсу робота в стартовом узле (для рабочего узла курс равен
`containerTheta`, иначе `request.RobotTheta`); во всех остальных случаях `0`.

Если курс робота неизвестен, допустимо оставить текущее поведение, но это надо отметить в коде.

### D4. Нет курса в первом узле

Сейчас `Routing:Order:FirstNodeTheta` по умолчанию `false` (`OrderOptions.cs:42`), и первый узел
уходит без `theta`. Эталон отдает курс фактической позы (`ref-pick-drop`, `wo-2-7`, `theta = 3.1357`).

Требуется: отдавать `theta` в первом узле, когда поза робота известна (`RobotTheta` не пуст).
Значение по умолчанию `FirstNodeTheta = true`.

### D5. Лишние поля ребер

Файл: `VdaOrderBuilder.cs`, `BuildEdge`, строки 357 и 364-367.

Убрать `maxSpeed` и `maxRotationSpeed` из тела ребра: эталон их не отдает ни в одном снимке.

## Ограничения

- Старый код AGVControl не переиспользовать, только поведение.
- Миграции не добавлять, таблицы `vrt_*` не менять.
- Планировщик A* не трогать.
- Приоритет: сохранность груза и стеллажей важнее времени цикла.

## Проверка

- Юнит-тесты на `VdaOrderBuilder`: действие только в целевом узле; отсутствие `maxSpeed`
  и `maxRotationSpeed`; `orientation = pi` на первом ребре при развороте; `theta` в первом узле.
- Тест на `RobotOrderService`: `from.Id == to.Id` для рабочего узла публикует заказ с действием.
- Живой прогон на стенде: задача `pick wo-2-7 -> drop wo-1-6`, снять заказ, сравнить
  `evidence/diff_same_route.py` с `ref-pick-drop-wo-2-7-wo-1-6.json`. Ожидается совпадение
  по узлам, действиям, курсам, допускам и набору полей ребер.
